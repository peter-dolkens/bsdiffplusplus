## 7. Everything else since 2006

Source for this section: a web survey done for this investigation (primary sources: source trees,
READMEs, papers; links inline). Items marked *unverified* could not be confirmed against a
primary source. Two claims that would change a recommendation were re-checked by hand: the
existence and README of the Rust bsdiff 6 reimplementation, and the .NET 11
`ZstandardEncoder.SetPrefix` API.

### 7.1 Two things that change the context of this project

- **bsdiff 6 has been reimplemented and measured.** A Rust reimplementation "faithful to the
  original (unpublished) bsdiff6 prototype" exists (Apache-2.0, 2026), with an NDSS SpaceSec 2026
  workshop paper. Its README states the thesis's design goal of roughly 20% smaller patches than
  bsdiff 4 and cites a measured improvement of about 5%. The survey's reading of the paper: average
  −4.8% versus bsdiff 4, smaller in 18 of 19 cases, ranging from −21.9% (glibc) to −0.06% (Linux
  kernel); every tool was packaged bsdiff-4 style with bzip2, so that number measures the alignment
  only, not the thesis's map/non-zero coder; the authors attribute the gain to the combination
  (DP) step, not to block alignment. HDiffPatch on the same corpus averaged −6.6%.
  <https://github.com/Julian-Rederle/bsdiff6>,
  <https://dev.ndss-symposium.org/wp-content/uploads/spacesec26-70.pdf>
- **Percival's own repository contains FFT block matching code** (`lib/blockmatch/blockmatch_psimm.c`,
  2012; `bsdiff-ra/`). The same paper measured bsdiff-ra at +0.9% versus bsdiff 4 on average.
  <https://github.com/cperciva/bsdiff>

Both agree with what is measured here: the DP alignment is worth 5% against bsdiff 4.3's under
the thesis coding, block alignment adds almost nothing once local alignment and the DP are
present (section 6.2), and the large gains are in the encoding stage, which the published
reimplementation did not measure.

### 7.2 Tools, one or two lines each

| tool | what it does differently from bsdiff 4.3 | take from it? |
|---|---|---|
| **Zucchini** (Chromium) | Disassembles PE/ELF/DEX to find references (x86 `rel32` by opcode heuristics, `abs32` only at reloc-table entries, ARM branch immediates; no ADRP/ADD pairs, no literal loads). Matches on a token view in which reference bodies are replaced by {type, label}, so matching sees through changed addresses; refines map and labels iteratively. Encodes each aligned reference as a signed *index delta* in a per-pool sorted target list after projecting the old target through the equivalence map; targets in inserted code are sent once per pool. No entropy coder; output is compressed externally (7z/brotli). [README](https://chromium.googlesource.com/chromium/src/+/main/components/zucchini/) | The projection step is the address prediction measured in section 4, reached there without a disassembler. What it has that section 4 does not: reference-aware *matching* and shared "extra targets" (bounded by the learned-target oracle of section 4.2). Its projection of targets that lie outside any equivalence is adopted in `addr.h` as extrapolation. |
| **Courgette** (Chromium, removed 2024) | Disassemble, replace internal pointers by indexes into an address table, bsdiff the two assembly forms, reassemble. Published example: bsdiff 704,512 bytes, Courgette 78,848. [design doc](https://www.chromium.org/developers/design-documents/software-updates-courgette/) | No: superseded by Zucchini; needs a full disassembler/assembler pair per platform on the apply side. |
| **AOSP bsdiff (BSDF2)** | Same algorithm with divsufsort; per-stream choice of bzip2 or Brotli, smaller kept. [source](https://android.googlesource.com/platform/external/bsdiff/) | Yes, and measured here: "try several back ends per stream, keep the smallest" (section 2). |
| **puffin / imgdiff / lz4diff / archive-patcher** | Undo deflate/LZ4 container compression deterministically, diff the uncompressed data, redo it on apply. | Out of scope (compressed containers), but the only way to patch `.zip`/`.gz`/APK-like inputs well. Not for this project now. |
| **HDiffPatch** | Suffix array (divsufsort) or block-hash streaming mode; "covers" selected with a compressor-aware cost; new−old over covers with zero-run RLE; zlib/bzip2/LZMA2/zstd back ends. README averages over 20 tar pairs: bsdiff 4.3 8.17%, its own matcher in bsdiff format 7.74%, with LZMA2 6.45%, zstd patch-from 7.57%; patch memory ~20 MB. [repo](https://github.com/sisong/HDiffPatch) | Two ideas: cost-aware cover selection (sections 6.3 and 9.2 here show that the DP's fixed costs are not tuned to the new coder), and LZMA as back end (section 2). |
| **ddelta, mendsley/bsdiff, qbsdiff** | bsdiff 4 with divsufsort and/or a streamable interleaved format. | The interleaved, streamable layout: yes (section 5). Nothing on ratio. |
| **bidiff** | Hash-table index instead of a suffix array, parallel scan, chunked zstd. | No: trades ratio for speed (section 6 measures what a crude hash aligner costs). |
| **detools** | bsdiff/HDiffPatch front ends plus "data format" modes for Cortex-M4 and AArch64: decodes `b`/`bl`/`adrp`/`add`/`ldr`/pointers, stores field differences in side streams and zeroes the fields before diffing. Its own README: "I don't recommend anyone to use this functionality as the gain is small in relation to memory usage and code complexity", and flags patent EP1988455B1. [repo](https://github.com/eerimoq/detools) | The cautionary data point for doing address handling as a *preprocessing transform*. Section 4 does it as model input instead, which needs no side streams and no field classification. |
| **xdelta3 / open-vcdiff** | VCDIFF copy/add with optional LZMA secondary compression; no approximate matching. HDiffPatch's table: xdelta3 13.6% vs bsdiff 8.17%. | No. |
| **zstd `--patch-from`** | Old file as an LZ77 prefix with long-distance matching; decode memory about the old file size. | Measured here as an outside reference (section 2.4): −14% against bsdiff 4.3 overall, +13% on patch pairs. LZMA2 with a preset dictionary does the same job 11 points better. .NET 11 exposes the zstd variant natively (`ZstandardEncoder.SetPrefix`). |
| **MSDelta / PatchAPI** | LZX-based delta with per-architecture preprocessing "transforms" applied identically on both sides (E8 call translation, relocation, import/export, .pdata, disassembly-based transforms for amd64/ARM). No public format spec. [docs](https://learn.microsoft.com/en-us/previous-versions/bb417345(v=msdn.10)) | Confirms the direction (make old resemble new using the alignment, then code the rest); nothing concrete to port. |
| **xz BCJ filters** (x86, ARM64 since 5.4, RISC-V since 5.6) | Convert relative branch targets to absolute before LZMA. | Measured: no gain on the extra string, and filter-then-bsdiff gains 2% on upgrades and loses 6% on patch pairs (sections 2.1, 4.6). |

### 7.3 Entropy coding

- **ANS** (rANS/tANS; zstd's FSE, LZFSE, JPEG XL): a faster replacement for static or
  semi-static arithmetic coding of multi-symbol alphabets. It does not help here: the gains
  measured in sections 3–5 come from *adaptive, context-conditioned binary* probabilities, and
  ANS decodes in reverse order of encoding, which is awkward for exactly that kind of model
  (adaptive binary coding with rANS needs the encoder to buffer and replay probabilities).
  A carry-less binary range coder is the right tool and is already in the project (`RangeCoder.cs`).
- **Context mixing** (lpaq/paq8/cmix/zpaq): the technique used in sections 3–5. The closest prior
  art for conditioning on the aligned old byte is LZMA's *matched literal* coding (after a match,
  the literal is coded bit by bit with the corresponding bit of the byte at `rep0` as context);
  with the old file as preset dictionary that is a (much weaker) form of the coder proposed here.
  Reference genome compressors (GeCo, GReEn) do the same with a copy model on a reference. No
  published general-purpose context-mixing *delta* coder for executables was found (*unverified
  absence*).

### 7.4 Theory after 2006

Exact k-mismatch: Clifford, Fontaine, Porat, Sach, Starikovskaya (SODA 2016),
O(n k² log k / m + n polylog m); Gawrychowski–Uznański (2018), Õ((m + k√m)·n/m). Approximate
text-to-pattern Hamming distance: Chan, Golan, Kociumaka, Kopelowitz, Porat (STOC 2020),
(1+ε)-approximation in O(ε⁻² n) by random sampling *without* FFT. Sparse FFT (Hassanieh, Indyk,
Katabi, Price 2012): O(k log n) for exactly k-sparse spectra. None of these changes the practical
picture: the thesis's method is already a randomised projection (mod primes) plus FFT with
O(m log n) total work, and its cost is not what limits this project (section 6). Whether any of
this line cites or supersedes the thesis's Chapter 1 is *unverified*.

### 7.5 Suffix sorting

libsais (Grebnov, 2021–): SA-IS, 4n bytes for the array plus ~16 KB, about 2.5× faster than
divsufsort single-threaded; no pure-managed port found on NuGet (`NLibSais` is a native binding).
Managed options that exist: `DeltaQ.SuffixSorting.SAIS` and `…LibDivSufSort` ("100% safe,
managed"), `SAIS-CSharp`. The project's own `SaIs.cs` is the right call; there is nothing to
take here beyond confirming that 4n (not 9n) is the state of the art for the array itself.
<https://github.com/IlyaGrebnov/libsais>, <https://github.com/jzebedee/deltaq>
